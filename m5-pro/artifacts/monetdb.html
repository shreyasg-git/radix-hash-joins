MonetDB Join Experiments

What MonetDB does when it joins two tables, the radix join it used to have, and how both did against the tuner's join on the tuner's data.

Short version.

  • MonetDB is a database built by two of the 1999 paper's authors. We downloaded its source code as of 25 November 2026, built it on the M5, and called its join code from our own small programs.
  • Today's MonetDB has no radix join. It joins with one big hash table on all of one table. Every size in it is a fixed number in the code; nothing picks settings by timing.
  • Experiment 1: MonetDB's own join on the tuner's tables took 4.48 to 7.88 times as long as the tuner's pick, and was slower in 40 of 40 rounds.
  • Until 2007 MonetDB had a radix join, written by Peter Boncz. We copied it out of MonetDB's history and ran it on the tuner's data: 486 of 486 answers were right.
  • Experiment 2: at the tuner's bits and passes, Boncz's join took 0.93 to 0.98 times the tuner's time up to 8,388,608 rows, and 1.03 times at 16,777,216. At the paper's formula it took 1.14 to 1.34 times as long, and lost 40 of 40 rounds.
  • Boncz's lead most likely comes from this data. His way of cutting reads each table once when the pieces come out equal, and on the tuner's data they always did. This has not been tested on uneven data.

Words used on this page

MonetDB

A free database program from the research institute CWI in Amsterdam. Peter Boncz and Martin Kersten, two of the radix-join paper's authors, built it.

Column

MonetDB keeps each column of a table as its own long list of values. MonetDB's code calls such a list a BAT.

Kernel

The bottom layer of MonetDB: the C code that does the work on columns, such as joining two of them. Its folder is gdk/.

Hash join

Put every row of table R into a table of boxes, chosen by a number worked out from its key. Then, for every row of S, look only in the box its key points to.

Radix join

The paper's join. First cut R and S into pieces by a few bits of each key's mixed number, then hash-join piece by piece, so each small hash table fits in the processor's cache.

Radix bits

How many bits choose the piece. B bits give 2B pieces: 11 bits give 2,048 pieces.

Pass

One trip through a whole table to cut it. With 2 passes, 10 bits are cut as 5 + 5.

Rows per box

How full a hash table is. 1/8 means 8 boxes for every row. The code calls a box a "bucket"; the list that links rows in the same box is the "link" list.

Key mixer

The small formula that turns a key into a scrambled number, so that keys spread evenly over the pieces and boxes. The tuner uses SplitMix64; Boncz used his own.

ns per row

The time of one whole join in nanoseconds (billionths of a second), divided by the rows in one table. Lower is faster.

Round

One run of every setting being compared, in a newly shuffled order, so a slow moment of the laptop lands on a different setting each time.

Checksum

One number summed from every matching pair of rows. Two joins with the same checksum and the same number of matches found the same pairs.

How a join runs in MonetDB today

A join written in the database language SQL goes down through 5 layers before any row is touched. Only the bottom layer does the join itself, and that is the layer our programs call directly.

sql/server/1. Read the questionThe SQL text is checked and turned into a plan of table operations: "join R and S where the keys are equal".
sql/backends/monet5/rel_bin.c2. Write a programThe plan becomes a list of instructions in MonetDB's own language, MAL. The join becomes one instruction, algebra.join.
monetdb5/optimizer/3. Rewrite the programMonetDB's optimizers rewrite the list. For threads, one of them (opt_mitosis.c) cuts the biggest table into row ranges, one join per range. It never cuts by key.
monetdb5/modules/kernel/algebra.c4. Run the programThe instruction algebra.join calls the C function ALGjoin, which calls the kernel's BATjoin.
gdk/gdk_join.c:48865. Join the columnsBATjoin picks a method and joins two columns. It returns two lists: the row positions of every matching pair.

How BATjoin picks its method

IfThen
Both columns are sortedMerge join: walk down both lists side by side.
One column is sorted, and searching it is cheaper by MonetDB's estimateFor each row of the other column, find its key in the sorted one by halving the search range.
Otherwise (the tuner's data: both shuffled)Hash join with one hash table on all of one column. A cost estimate (joincost) picks which column gets the table.

Its hash table

Boxes
Rows × 8/7, at least 256 (HASHmask, gdk/gdk_private.h:186). That is 0.875 rows per box, fixed.
Links
One per row, to chain rows that land in the same box.
Entry size
2 bytes up to 65,535 rows, 4 bytes up to 4,294,967,295 rows, else 8 bytes (HASHwidth, gdk/gdk_hash.c:42).
Kept
The table stays attached to the column after the join, is used again by the next join on that column, and is saved to disk for stored tables.

The new pipeline engine

MonetDB 2026 also has a second, newer way to run queries, called the pipeline engine. It is off unless turned on (SET pipeline = true; the default is in mal_client.c:57). Its join uses one shared hash table sized at the estimated rows × 2.52, rounded up to a power of 2. It does not cut by key either.

A first look through SQL, not saved

To check that the build works end to end, we started the MonetDB server, made two tables of 16,777,216 rows with 8-byte keys, and ran SELECT sum(r.k) + sum(s.k) FROM r JOIN s ON r.k = s.k 5 times in each of 3 ways. Its plan showed the one algebra.join instruction. The data is not the tuner's (R's keys are 0 to 16,777,215 in a mixed order; S's are spread over twice that range), so these times are not comparable with the rest of this page.

The radix join MonetDB used to have

Peter Boncz wrote a radix join module for MonetDB, in the file radix.mx: radix_cluster cuts a column into pieces and phash_join joins two cut columns piece by piece. MonetDB's history shows when it went away.

DateWhat happenedCommit
2007-09-12The last version of MonetDB that compiled the radix module. Our copy is made from this one.33a91903a7
2007-10-04The build file turned it off (#radix.mx) in a large merge called "Merged GDK-2 branch".892ef9b796
2007 to 2012The file stayed in the source code without being compiled. The older MonetDB4 line had it turned off by 2011 too.
2012-03-28The file was deleted.0adbe4238f
  • The core functions are the same in the 2007 and 2011 copies, apart from renamed variables and one fix so a shift works on 64-bit computers.
  • It never ran by itself. SQL never used it. A person wrote the plan by hand and typed the bits of every pass, for example radix_cluster(b, 6, 5).
  • An earlier version of the notes said the last release with the radix join was Dec2011-SP2. That was wrong, and was corrected on 26 November: Dec2011-SP2 still contains the file, but does not compile it.

Experiment 1: MonetDB's join on the tuner's data

A small C program starts MonetDB's kernel inside itself, with no server and no SQL. It makes the tuner's two tables with the tuner's own code, copies their keys into MonetDB columns, calls BATjoin, and checks the number of matches and the checksum against the tuner's answer. It went in 4 steps, each checked before the next.

Data
The tuner's: N rows per table. R's keys are 0 to N−1; S's keys are 0, 2, 4, …, so half of S finds a match. Both shuffled with seed 42.
MonetDB
Downloaded at commit f17907b909 (25 November 2026, version 56.0.0) and built with its release settings by setup.sh.
Tuner's join
Its own code, unchanged, at its picks from the race of 24 November.
Thread

Step 2: what MonetDB did, from its own messages

  1. Checked whether either column is sorted. Neither is; this took under 1 ms.
  2. Looked at 1,000 rows of each column to guess how many different keys there are. All 1,000 differed.
  3. Picked a hash join and built a new hash table on R.
  4. Made 1,198,372 boxes (1,048,576 × 8/7), plus one link per row. 685,625 boxes got at least one row.

At 16,777,216 rows MonetDB's hash table and keys take about 211 MB: boxes 77 MB, links 67 MB, keys 67 MB. The M5's second cache holds 16 MB. So most lookups wait for main memory, which is the slowdown the radix join was invented to avoid.

Result
  • The tuner's pick beat MonetDB's join in all 40 of 40 rounds. MonetDB took 4.48 times as long at 1,048,576 rows and 7.31 to 7.88 times from 4,194,304 rows up.
  • From 1,048,576 to 16,777,216 rows the tuner's join slowed down 1.19 times, MonetDB's 2.09 times. The radix join keeps each piece's hash table in the cache; MonetDB's one table stops fitting.
  • MonetDB's time includes 1.07 to 2.40 ns per row to turn its list of pairs into the tuner's checksum, because the tuner's join makes its checksum inside its own timing. The rest, 40.12 to 83.75 ns per row, is BATjoin.
  • MonetDB said "hashjoin using new hash; create hash" in all 40 of its timed joins: it built a new table every time and never reused one.

Experiment 2: Boncz's radix join, copied

We copied radix_cluster and phash_join from the 2007 file into one C file of 340 lines, boncz_radix.h, that works on the tuner's rows. Next to each function it names the line of the original it comes from, so every line can be checked. MonetDB's license covers the original, so the original is not committed; fetch-original.sh saves it from MonetDB's history. The copy needs no MonetDB build.

Same idea, different details

Tuner's joinBoncz's join (MonetDB 2007)
Key mixerSplitMix64 (mix)(x>>7) ^ (x>>13) ^ (x>>21) ^ x (int_HUSSLE, radix.mx:1270)
One pass of cuttingCount every row's piece, then move every row: 2 reads of the tableGive every piece an equal share of space and move rows until one share is full. Then guess the rest from what was moved, or count it, shift the pieces to make room, and finish. If no share fills up: 1 read (radix.mx:2053)
Finding the pieces when joiningA list of where each piece startsWalk both cut tables side by side and find runs of rows with the same piece number (radix.mx:2791)
Hash tablesOne per piece; boxes = rows ÷ rows per box, a settingOne, reused and emptied for each piece; boxes = the smallest power of 2 at least R's average piece size
Box and link entries4 bytes8 bytes (2007's default on 64-bit computers)

What the copy changes, and why

  • Rows: the tuner's 8-byte rows (a 4-byte key and a 4-byte row number), so both joins read the same data. Boncz's original rows were about 12 bytes. The two byte limits in his code are turned into row counts: 32,768 bytes became 4,096 rows.
  • Memory: each pass writes into memory the tuner sets up before the clock starts. The original made a new column for every pass. The small arrays (counts, hash table) are still made inside the join, as in the original.
  • Matches: each match is added to the checksum, as the tuner's join does, instead of being written out.
  • Stopping early: the original stopped at the first match when R's keys were known to be unique. The copy can do both, and the timed runs never stop early, like the tuner.
  • Safety: one copy of memory onto itself uses memmove, which is defined when the two areas overlap, instead of memcpy.

Step 1: how Boncz's cuts finished

Across all 486 checks his code made 34,420 cuts. 30,964 of them (90.0%) fitted the equal shares and read the table once. 3,456 (10.0%) had to count the rest, 6 of those after first guessing it. The tuner's keys are consecutive numbers, and his mixer spreads consecutive numbers almost evenly, so his "equal shares" guess is usually right on this data.

What these results do not show

Exp. 1: memory
open MonetDB makes the memory for its hash table and its two result lists inside the timed join. The tuner's join uses memory set up before the clock starts. How much of MonetDB's time that is has not been measured.
Exp. 1: output
open MonetDB writes out every matching pair: two lists of 524,288 positions at 1,048,576 rows. The tuner's join only adds them up. A database needs the pairs to fetch other columns afterwards.
Exp. 1: tuner's speed
open The tuner's pick ran faster here than in the race of 24 November with the same code and settings: 9.20 against 10.51 ns per row at 1,048,576 rows. Here it alternated only with MonetDB; in the race, with 4 other settings. Why has not been tested.
Exp. 2: the data
open Boncz's lead comes with cuts that never had to count, which happens because the tuner's keys are consecutive. Uneven keys would make his cuts count too. Not tested.
Exp. 2: the picks
open The tuner's picks were found for the tuner's join. Boncz's join may have different best settings. Not tested yet: that is the next step.
Exp. 2: 16M rows
open Why Boncz's join loses at 16,777,216 rows has not been tested. Two differences that could matter: his entries are 8 bytes against the tuner's 4, and his hash tables hold 1 row per box against the tuner's 1/8.
Both
open 1 thread, 1 machine, 1 data set (unique keys, both tables the same size, half of S matching), 1 run of each experiment.
Answers
checked Every timed join's matches and checksum were checked against the tuner's expected answer. A wrong answer stops the program.

What comes next

  1. Let the tuner search Boncz's settings (experiment 2, step 4). The tuner's search can only time the tuner's own join. Two ways: add a switch to tuner/src/tune.c that changes nothing unless it is turned on, or copy the search into the experiment 2 folder. Waiting for your choice.
  2. Uneven keys. Run both radix joins on keys that bunch up, to see whether Boncz's one-read cut still wins once it has to count.
  3. Find the 16M-row loss. Change Boncz's join one detail at a time at 16,777,216 rows: 4-byte entries, then 1/8 row per box.
  4. MonetDB's memory cost. Time how long MonetDB spends getting memory inside its join, to make experiment 1 fairer.
