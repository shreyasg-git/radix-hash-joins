hash_join.c

Experiment 2: the simple hash join. File: m5-pro/src/hash_join.c, 341 lines.

The short version. A join pairs up the rows of two tables whose key is equal. This program does it in two steps. Build: put every row of the left table into a lookup structure, indexed by a scrambled copy of its key. Probe: for each row of the right table, look in that structure for left rows with the same key. It does this at 6 table sizes (10,000 to 5,000,000 rows), times each step, and writes the times to a file. It is the baseline the radix join is compared against.

M5 version vs main version. This file is a copy of src/hash_join.c with 3 changes for the Mac: a nanosecond timer, a request for the fast cores instead of pinning to one core, and a build switch for the bucket rule. By default it uses at least 2 buckets per left row. If you compile with -DQUARTER_BUCKETS it uses about 1 bucket per 4 left rows, which is the rule in the main-branch file. Everything else is the same.

The data types

Four small structures lines 24–45

What
  • Record: one row. key is the value we join on. row_id is the row's position in its original table. 8 bytes.
  • Pair: one result. The left row's row_id and the right row's row_id.
  • HashTable: the lookup structure. records points to the left rows. buckets[b] holds the index of the first left row in bucket b, or SIZE_MAX if the bucket is empty. next[i] holds the index of the next left row in the same bucket as row i, or SIZE_MAX at the end. bucket_count is the number of buckets.
  • JoinResult: what probe returns. matches (how many pairs were found) and checksum (one number that fingerprints all pairs).
Each bucket is a chain of rows linked by array positions. There is no separate allocation per row.

Build and probe

build lines 80–99

Input
The left rows and their count.
Returns
A HashTable.
What
  1. Picks the bucket count: the smallest power of two that is at least 2 × count (default), or at least ceil(count / 4) with -DQUARTER_BUCKETS. Zero rows still gets 1 bucket.
  2. Allocates buckets and next, and sets every bucket to empty.
  3. For each left row, computes mix(key) & (bucket_count - 1). Because the count is a power of two, this one bit-mask does the job of a remainder. Then inserts the row at the front of that bucket's chain: next[i] takes the old first row, and buckets[bucket] takes i.
With the default rule a bucket holds at most about 0.5 rows on average. With the quarter rule it holds between 2 and 4.

probe lines 101–123

Input
The table, the right rows, their count, and optionally an output buffer for pairs (pairs, capacity).
Returns
A JoinResult.
What
For each right row, finds its bucket the same way and walks that bucket's chain. Different keys can share a bucket, so it compares records[row].key == right[i].key on every row. On a match it builds a Pair of the two row_ids, saves it only if pairs is not NULL (and stops with an error if the buffer is full), adds 1 to matches, and adds mix(pair) to checksum.
The benchmark passes NULL, so it only counts. The tests pass a buffer so they can compare every pair. The checksum uses addition, so the order pairs are found in does not change it.

release lines 125–128

What
Frees buckets and next. It does not free the left rows, because the table does not own them.

The correctness test

reference_join and compare_pairs lines 130–147

What
reference_join is the slow, obviously correct join: it compares every left row with every right row (a nested loop) and returns the pairs. compare_pairs orders pairs by left row, then right row, so two lists can be compared after sorting.

check_case lines 149–166

Input
A name and two small tables.
What
Runs the reference join and the hash join on the same input, sorts both outputs, and compares the counts and every byte of every pair. Prints FAIL: <name> and exits on any difference.

random_next and self_test lines 168–200

What
random_next is a small repeatable random number generator: it adds a fixed constant to its state and runs the result through mix. self_test (run with --test) runs 107 cases:
  • 6 hand-written cases: duplicates with the smallest and largest keys (0 and 4,294,967,295), no matches, empty left, empty right, both empty, and all rows matching all rows.
  • 1 case with 3 different keys that land in the same bucket. The loop picks keys where mix(key) & 7 == 0. With the default rule, 3 rows get 8 buckets, so the filter is correct: they really do share bucket 0 of 8. (With the quarter rule there is 1 bucket and the filter does nothing, but the test still passes.)
  • 100 random cases: 32 left rows, 48 right rows, only 11 distinct key values, so there are many duplicates.

Making the benchmark data

shuffle and generate lines 202–218

What
shuffle puts rows in random order (a standard Fisher-Yates shuffle). generate fills two tables of count rows. Left keys are 0, 1, 2, … count-1. Right keys are 0, 2, 4, … 2*(count-1). Each row_id is the original position. Both tables are then shuffled with seed 42.
Result
Every key is unique, and exactly the even keys below count match: ceil(count / 2) matches. For 1,000,000 rows that is 500,000. The right answer is known in advance, with no second join needed.

main

The benchmark lines 263–341

Usage
hash_join --test runs the self-test. hash_join OUTPUT_DIRECTORY [REPEATS] [MAX_ROWS] runs the benchmark. REPEATS defaults to 7 (allowed 1–100). MAX_ROWS defaults to 2,000,000 (allowed 10,000–5,000,000).
Steps
  1. Creates the output directory with mkdir. This fails if the directory already exists, so old results are never overwritten.
  2. Asks for the fast cores. Opens timings.csv and environment.txt. The second records the compiler, record size, timer, seed (42), repeat count, and which bucket rule was compiled in.
  3. For each size in {10,000; 100,000; 500,000; 1,000,000; 2,000,000; 5,000,000}, stops once the size passes MAX_ROWS:
    • allocates and generates both tables;
    • computes the expected match count and checksum from the known data: left row i pairs with right row i/2 for every even i;
    • runs repeats + 1 times. Run 0 is a warm-up and is not recorded. Each run times build and probe, checks the matches and checksum against the expected values, and stops with "Generated-data result mismatch" if they differ;
    • writes one CSV row per recorded run, then frees the table and flushes the file;
    • prints <rows> rows per input: verified <matches> matches; <n> recorded runs.
Output
timings.csv columns: rows_left, rows_right, run, seed, matches, checksum, buckets, estimated_bytes, build_ms, probe_ms, total_ms.
estimated_bytes = 2 * count * 8 (the two tables) + (count + bucket_count) * 8 (bucket array and chain links, 8 bytes each).

Why the size matters

Both tables always have the same size, every key is unique, and half the right rows match. So the only thing that changes between sizes is how big the lookup structure is. Each probe reads a random bucket. While the structure fits in the processor's cache (the small, fast memory next to each core), most reads are fast. Once it is bigger, most reads go to main memory, which is slow.

Example with the default rule at 1,000,000 rows: 2,097,152 buckets × 8 bytes = 16.8 MB, plus chain links 8.0 MB, plus left rows 8.0 MB, about 32.8 MB. The M5's largest cache (L2) is 16 MB. At 100,000 rows the same arithmetic gives 262,144 × 8 = 2.1 MB, plus 0.8 MB, plus 0.8 MB, about 3.7 MB, which fits.
