radix_join.c

Experiment 4: simple hash join versus radix hash join. File: m5-pro/src/radix_join.c, 358 lines. It uses shared helpers from m5-pro/include/common.h.

The short version. The simple join builds one big lookup table on the whole left table. Once that table is bigger than the processor's cache (the small, fast memory next to each core), almost every lookup goes to slow main memory. The radix join adds a first step to avoid that:

  1. Partition: split both tables into 2^bits groups, using the low bits bits of the scrambled key. Matching keys always land in the same group number in both tables.
  2. Join each pair of groups: for group p, build a small lookup table on the left group and probe it with the right group. Each small table is meant to fit in the cache.

Partitioning costs extra passes over all the data. The experiment asks when that cost is paid back. The same file also runs the simple join, so both are timed under the same rules.

Why shift = bits in the radix join. Inside one partition, every key has the same low bits bits. If the buckets used those same bits, all rows would pile into a few buckets. So the radix join takes buckets from the bits above them. The simple join uses shift = 0.

What
States the design rules: buffers are allocated before timing; filling buckets with EMPTY counts as build time; partition, build and probe are timed separately. partition_all lines 53–79

Input
A table, its row count, bits, passes, and the buffers.
Returns
A pointer to the partitioned rows. Through *bounds it also returns the 2^bits + 1 positions where partitions start and end.
What
Starts with one group holding everything. Each pass splits every group on the next bit group, starting with the highest of the low bits bits and working down. Using several smaller passes instead of one big one keeps the number of places written to at once small. The input table is never changed. The output flips between buffer a and buffer b each pass.
Result: partition p holds exactly the rows whose mix(key) has low bits bits equal to p.

radix_join lines 98–156

Input
Both tables, bits, passes, the buffers, and optional counters.
Returns
JoinTimes.
What
  1. Times the partitioning of the left table (partition_r_ms) and the right table (partition_s_ms).
  2. Loops over partitions 0 to 2^bits - 1. Each time it builds a small table on left partition p (with shift = bits) and probes it with right partition p. The same buckets and next arrays are reused every time.
Two timing modes:
  • Clean (default): no clock reads inside the loop. The build time comes from a second, build-only pass run right after the join; that pass is not part of the total. Probe time = join time − build time. So in this mode the build and probe times are an estimate; the totals are exact.
  • Per-partition: two clock reads per partition, the older way, kept to show the difference.

One thing I noticed. In clean mode the last counter reading (c2, line 148) is taken after the extra build-only pass. On Linux the join_ counter columns would therefore include that extra pass. The M5 has no counters, so those columns are empty there. I did not check whether any report uses them.

main lines 247–358

Usage
radix_join --test, or radix_join OUTPUT_DIRECTORY [--sizes] [--bits] [--passes] [--repeats] [--seed] [--timing clean|per-partition].
Defaults
Sizes 100,000 / 1M / 2M / 4M / 8M / 16M / 32M rows per table. Bits 0, 2, 4, … 18 (0 means the simple join). Passes 1 and 2. Repeats 15. Seed 42.
Setup
Creates a new results folder (fails if it exists). Asks for the fast cores. Writes environment.txt (including the cost of one clock read and the timing mode) and the timings.csv header.
For each size
  1. Allocates both tables, buffers and lookup arrays before any timing. Generates the data and the expected answer.
  2. Builds the list of settings. Skips any bits where 2^bits > rows / 4 (fewer than about 4 rows per partition; for 100,000 rows that limits bits to 14 or less). Skips settings with more passes than bits. The simple join is listed once.
  3. Runs repeats + 1 rounds. Round 0 is a warm-up and is not recorded. Every round runs every setting once, in a newly shuffled (but repeatable) order.
  4. After each join, checks matches and checksum against the expected values, and stops on a mismatch.
  5. Writes one CSV row per setting per recorded round.
Output
timings.csv columns: rows_per_input, algorithm, total_bits, passes, run, position, steal_ms, partitions, max_partition_rows, partition_r_ms, partition_s_ms, build_ms, probe_ms, join_ms, total_ms, matches, then the partition_ and join_ counter columns.

The simple join inside radix_join.c uses the same table code as the radix join (32-bit links, at-most-half-full tables), so the comparison inside this experiment is like for like. That differs from the stand-alone hash_join.c, which uses 64-bit links.
