parallel_join.c

Experiment 5: the simple and radix joins on 1, 2 and 4 threads. File: m5-pro/src/parallel_join.c, 479 lines. It uses shared helpers from m5-pro/include/common.h.

The short version. A thread is one line of work that runs on its own core. This program runs both joins with several threads at once and asks: how much faster does the join get with 2 or 4 threads than with 1?

  • Simple join: all threads share one lookup table. In the build, each thread inserts its slice of the left table. In the probe, each thread looks up its slice of the right table.
  • Radix join: the threads split the partitioning work, then hand out whole partitions to each other. Each partition gets its own small table.

After every phase all threads wait for each other at a barrier, so each phase has a clean time.

The M5 fix ("flaw 2", header lines 32–41). The older version inserted rows into the shared table with a "compare-and-swap in release order", which made each core finish every earlier memory write before each insert. On the M5 that made the 1-thread build take 540 ms instead of 80 ms, so the simple join's speed-up with more threads looked better than it is. Now each insert is one atomic swap: old = swap(head, i); next[i] = old. That is safe because no thread reads the table until all threads have passed the barrier after the build. --insert cas-release brings back the old way to show the difference.

The barrier lines 49–80

What
macOS has no built-in barrier, so this is a small one made from a lock and a signal. barrier_wait counts the threads that have arrived. The last one to arrive resets the count, bumps a generation number, and wakes everyone. The others sleep until the generation changes. barrier_init and barrier_destroy set it up and clean it up.

partition_side lines 124–184

Input
The shared data, one side (left or right), and the thread's number.
What
Pass 1 in three steps, with no locks:
  1. Each thread counts the rows of its own slice per group, into its own row of histogram. Barrier.
  2. Each thread works out where in each group its rows should go: the total of all earlier groups, plus the counts of the threads before it. So no two threads ever write the same slot. Thread 0 also writes the group boundaries.
  3. Each thread copies its slice's rows to those slots. Barrier.
Later passes: whole groups are handed out. Each thread takes a group number from the shared counter (__atomic_fetch_add), splits that group alone with radix_pass into private boundary space, and copies the boundaries into the shared array. Barrier. Thread 0 then writes the final boundary and resets the counter. Barrier.
At the end thread 0 records which buffer holds the result.

worker (the thread body) lines 188–261

What
Each thread asks for the fast cores, waits at a barrier, and thread 0 writes down the start time. Then:

Simple join

  1. Each thread clears its slice of the bucket array to EMPTY. Barrier.
  2. Each thread inserts its slice of the left table into the shared table (with the atomic swap, or with compare-and-swap if --insert cas-release). Phase 1 ends.
  3. Each thread probes its slice of the right table against the shared table, using hash_probe, into its own result. Phase 2 ends.

Radix join

  1. Partition the left table (phase 1), then the right table (phase 2).
  2. Thread 0 lays out all the small tables in one array: it adds up bucket_count_for(rows) for each partition. This is counted as build time. Barrier.
  3. Build: threads take batches of 16 partitions from the shared counter. Each builds a small table for its partitions using hash_build (shift = bits). Each partition's chain links sit at the same positions as its rows, so no two threads touch the same entries. Barrier. Thread 0 notes the time and resets the counter.
  4. Probe: threads take batches again. Partition p of the right table is looked up in the small table of partition p of the left table. Phase 4 ends.
Each thread saves its own match count and checksum.

Setup shared by the test and benchmark lines 265–341

What
  • RunTimes: up to 4 phase times (simple: build, probe; radix: partition R, partition S, build, probe), the total, and the combined result.
  • context_init: allocates every buffer once, sized for the biggest case, and writes them before any timing. The bucket array is sized as the larger of 4 × rows + 2max_bits + 2 (enough for all the small tables) and the simple table's size. context_free frees them.
  • run_join: sets up the shared data, starts the threads, waits for all of them to finish, turns the phase stamps into milliseconds, and adds up the threads' match counts and checksums. (Both are sums, so the order does not matter.) Returns RunTimes.

main lines 403–479

Usage
parallel_join --test, or parallel_join OUTPUT_DIRECTORY [--rows N] [--threads 1,2,4] [--bits B] [--passes P] [--repeats R] [--seed S] [--insert swap|cas-release].
Defaults
16,000,000 rows per table, threads 1, 2 and 4, 14 bits, 1 pass, 15 repeats, seed 42.
Steps
  1. Creates a new results folder and writes environment.txt (including which insert method is used).
  2. Makes the data once, and allocates all buffers once.
  3. Lists the combinations: each thread count × {simple, radix}. Runs repeats + 1 rounds; each round runs every combination once in a new shuffled order. Round 0 is a warm-up.
  4. Checks every run's matches and checksum against the known answer and stops on a mismatch.
  5. Writes one CSV row per phase, plus one row named total.
Output
timings.csv columns: rows_per_input, algorithm, threads, total_bits, passes, run, position, steal_ms, phase, ms.

Things I noticed

  • The radix build and probe are separate phases here (all small tables are built, then all are probed). The header says so: each small table is read again from memory at the start of its probe, which costs a little compared with the 1-thread program in radix_join.c. So the radix times here are not directly comparable with experiment 4's.
  • On macOS, threads cannot be pinned to cores. pin_to_cpu only sets the high quality-of-service class, so which core each thread lands on is up to the scheduler.
  • steal_ms is -1 on macOS, so that CSV column carries no information on the M5.
