scan_benchmark.c

Experiment 1: the stride scan. File: m5-pro/src/scan_benchmark.c, 197 lines. It does not include common.h; it is stand-alone and only builds on a Mac with Apple silicon.

The short version. This program has nothing to do with joins. It measures how the memory of this Mac behaves. It reads 200,000 single bytes from a 256 MB block, with a fixed gap (the stride) between each read: 1, 2, 4, 8, … up to 1,024 bytes. It times each scan. Two things show up in the times:

  • The cache line. Memory is copied into the cache in chunks of 128 bytes on this Mac. With a gap under 128 bytes, several reads fall inside the same chunk, so one copy serves many reads. With a gap of 128 or more, every read needs a new chunk.
  • Cached or not. Each scan runs two ways: flushed (the caches are emptied first) and repeat_scan (the same data was just read, so it may still be in the cache).

The later experiments rely on these numbers to explain why a big lookup table is slow.

The changes from the original (header, lines 1–25)

This is the Mac version of src/scan_benchmark.c, which was written for x86 Linux. There are 5 changes:

  1. Emptying the cache. The original used the x86 CLFLUSH instruction. Its ARM counterpart (DC CIVAC) runs on macOS but has no measurable effect: random reads of 512 KiB took 2.6 ns each before and after it. So this program reads a separate 512 MB block instead, far larger than every cache on the chip, which pushes the scan's data out. This also empties the address-translation cache.
  2. The cache line size is read from sysctl hw.cachelinesize (128 bytes on the M5).
  3. The timer is CLOCK_UPTIME_RAW (ticks of 41.7 ns) instead of CLOCK_MONOTONIC.
  4. No thread pinning. The thread asks for the highest quality-of-service class, which runs on the fast cores.
  5. Ordering barriers are DSB + ISB instead of LFENCE/MFENCE.

scan lines 53–58

Input
A pointer to the data and a stride.
Returns
The sum of the 200,000 bytes read (at most 200,000 × 255 = 51,000,000, which fits in 32 bits).
What
Reads one byte, moves forward by stride bytes, and repeats 200,000 times. The pointer is volatile, which stops the compiler from skipping the reads. The sum is a checksum: it proves the reads really happened and always gives the same answer.

evict_caches lines 60–69

What
Reads one byte of every 128-byte line of the separate 512 MB block, stores the sum somewhere the compiler cannot ignore, then runs a barrier. Afterwards the caches hold that block instead of the scan data.

open_output lines 71–75

What

eviction_check lines 77–119

Returns
Three numbers through pointers: nanoseconds per read when the data is cached, after DC CIVAC, and after reading the 512 MB block. Each is the best of 5 tries.
What
A check that the cache-emptying method works. It builds a chain of 4,096 lines (512 KiB) in random order, where each line holds the position of the next. Following the chain is a series of reads where each read must finish before the next can start, so they cannot overlap and the time per read is the true delay. It times the chain three ways and re-reads it between tries.

main lines 121–197

Usage
scan_benchmark [OUTPUT_DIRECTORY] [repetitions]. Folder defaults to results. Repetitions default to 30 (allowed 5–1,000).
Setup
Creates the folder, asks for the fast cores, reads the cache line size, allocates the 256 MB scan block and the 512 MB eviction block (both aligned to 16 KB, the page size), fills the scan block with random bytes, and computes the expected checksum of every stride.
Writes
  • benchmark_metadata.json: platform, CPU name, timer, settings, and the three numbers from eviction_check.
  • timer_overhead.csv: 1,000 samples of two back-to-back clock reads, to show the clock's resolution.
  • raw_timings.csv: one row per timed scan. Columns: round, order, condition, stride_bytes, reads, address_span_bytes, selected_cache_lines, elapsed_ns, checksum.
The loop
  1. Runs rounds numbered −3 up to repetitions − 1. The 3 negative rounds are warm-ups and are not recorded.
  2. Each round has 22 jobs: 11 strides × 2 conditions, shuffled into a new order every round.
  3. For a repeat_scan job it first runs the scan once, untimed. For a flushed job it runs evict_caches.
  4. Then barrier, read the clock, scan, barrier, read the clock. If the checksum differs from the expected one, it stops with code 3.
  5. Records address_span_bytes = 199,999 × stride + 1, and selected_cache_lines: for strides under 128, the span divided by 128 rounded up; for 128 or more, simply 200,000 (one line per read).

Things I noticed

  • It reuses an existing folder. Line 125 accepts a folder that already exists (errno != EEXIST). The other programs refuse. Files with the same names inside it are overwritten.
  • repeat_scan does not guarantee a cached read. At strides of 128 and up, a scan touches 200,000 different 128-byte lines, which is 25.6 MB. The M5's largest cache (L2) is 16 MB, so at those strides the data cannot all stay cached. repeat_scan means "right after reading the same data", not "fully in cache". I have not looked at the results to see how this shows.
  • There is no --test mode in this program. Its only check is the checksum of every scan.
