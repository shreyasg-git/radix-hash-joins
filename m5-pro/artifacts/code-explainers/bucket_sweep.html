bucket_sweep.c

Experiment 6: how many buckets, and which hash function? File: m5-pro/src/bucket_sweep.c, 607 lines. It uses shared helpers from m5-pro/include/common.h.

The short version. The earlier experiments chose the number of buckets by a rule (at least 2 per row in week 2, about 1 per 4 rows in a later commit) and used one hash function, mix. Neither choice was ever measured. This program measures both. It runs the simple and radix joins over every combination of:

  • Load: how many left rows per bucket on average (1/16 up to 8 by default).
  • Hash function: 5 choices (below).
  • Key pattern: 3 choices (below).
  • Table size: 65,536 / 524,288 / 4,194,304 / 16,777,216 rows by default.

For each setting it records the time and also how evenly the keys spread over the buckets.

The five hash functions (lines 85–119)

The bucket is always taken from the low bits of the hash. In the radix join, the partition uses the low bits and the bucket uses the bits above them.

NameWhat it computesWhy it is in the test
identitythe key itselfThe simplest possible choice. Spreads dense keys perfectly, but pile-ups are likely on regular keys.
multiply-lowkey × 0x9E3779B97F4A7C15, low bitsThe low bits of a product depend only on the low bits of the key, so this can still pile up.
fibonaccithe same product, with the bits reversed so the top bits come firstThe top bits of the product depend on every key bit (Knuth's multiplicative hashing).
crc32the processor's CRC-32C instructionA hash built into the hardware. Uses the ARM instruction on the M5.
mixSplitMix64 scramblerThe one used in every other experiment.

The three key patterns (lines 121–149)

NameKey number j isMeaning
densej0, 1, 2, 3 … The pattern used in every other experiment.

Left row i gets key k(i). Right row i gets key k(2i). Both tables are shuffled. Since k never repeats, exactly the right rows with 2i < N match, so every pattern has the same known answer as the other experiments: ceil(N / 2) matches.

The hash table lines 151–205

What
  • buckets_for(rows, load): the smallest power of two that is at least ceil(rows / load). So load is "rows per bucket". Load 0.5 gives the week-2 rule; load 4 gives the later rule.
  • build_h: like hash_build in common.h, but takes the hash function and bucket count. Sets all buckets to empty (counted as build time), then inserts every row at the front of its bucket's chain.
  • probe_h: like hash_probe, with the chosen hash.
  • partition_h: one radix pass on the low bits bits of the chosen hash: count, running total, copy, then shift the boundaries back by one. Always a single pass here.

radix_join lines 240–272

What
Partitions both tables (timed as partition_ms). Then loops over partitions, building a small table on each left partition (with buckets_for of that partition's size, using the bits above the partition bits) and probing it with the matching right partition. Only the whole loop is timed, with no clock reads inside. Then it repeats just the builds in a second pass to split the time: build_ms is that pass, and probe_ms is the join time minus it (never below 0). The second pass is not in the total. The buckets value is the sum over all partitions.

How evenly the keys spread lines 274–322

Returns
A Spread: total buckets, buckets that hold at least one row, the longest chain, partitions with rows, the largest partition, and rows checked per probe.
What
This runs once per setting, before any timing, and is not timed. spread_of_table counts the left rows in every bucket. A probe walks its bucket's whole chain, so the rows checked per probe is the average chain length over the buckets that the right rows land in. A hash that piles keys into few buckets shows up here as long chains and many empty buckets. measure_spread does this for the simple join (one table) or, for the radix join, for every partition's table and adds them up.

What

main lines 494–607

Usage
bucket_sweep --test, or bucket_sweep OUTPUT_DIRECTORY [--sizes] [--loads] [--hashes] [--keys] [--joins] [--bits auto|B] [--repeats R] [--seed S].
Defaults
4 sizes; loads 0.0625, 0.125, 0.25, 0.5, 1, 2, 4, 8; hash mix; keys dense; both joins; bits auto; 7 repeats; seed 42.
Steps
  1. Creates a new results folder (fails if it exists). Writes environment.txt.
  2. For each size: makes the key patterns it needs (stride64 needs at most 225 rows or the keys would overflow 32 bits), allocates the buffers, and builds the list of settings. The radix join is skipped if 2^bits > rows / 4. With the defaults that is 2 joins × 8 loads = 16 settings per size.
  3. Measures the spread of every setting and writes distribution.csv.
  4. Runs repeats + 1 rounds, each setting once per round in a newly shuffled order. Round 0 is a warm-up. Every run's matches and checksum are checked and the program stops on a mismatch.
  5. Writes one timings.csv row per recorded run.
Output
  • timings.csv: rows_per_input, join, hash, keys, rows_per_bucket, bits, buckets, run, position, partition_ms, build_ms, probe_ms, join_ms, total_ms, matches.
  • distribution.csv: rows_per_input, join, hash, keys, rows_per_bucket, bits, buckets, actual_rows_per_bucket, empty_bucket_share, longest_chain, rows_checked_per_probe, partitions, partitions_used, largest_partition_rows.
  • environment.txt.

Things I noticed

  • The radix join here always uses 1 pass (radix_passes=1 in the environment file), and the number of bits is fixed per size (auto), so this experiment does not vary the radix settings.
  • The load list sets the maximum rows per bucket, but because the bucket count is rounded up to a power of two, the real load is lower. That is why distribution.csv has an actual_rows_per_bucket column.
  • With the radix join, the largest chain and the partition sizes are measured across all partitions, so one badly spread partition shows up in longest_chain even if the others are fine.
