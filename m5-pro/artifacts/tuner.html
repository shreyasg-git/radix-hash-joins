Radix Join Tuner

How the tuner picks the radix join's 3 settings, what it found on the M5, how correct and fair it is, and the paper's formulas for the same settings worked out for this Mac.

Short version.

  • The tuner times the radix join at hundreds of settings on the computer it runs on and keeps the fastest. It never reads the computer's cache sizes.
  • On the M5 it ran 937 timed joins in 2 minutes 0 seconds. The fastest setting at every size was 1 pass and 1/8 row per box, with 10 to 12 bits: 9.92 to 11.00 ns per row.
  • It is correct: every timed join's answer was checked, and its 191,213-check self-test passes.
  • It has 5 weak points in fairness. The biggest: its "2.68 times as fast as no cutting" compares against a no-cutting join that was never tuned. With both joins at 1/8 row per box, the gain was 1.89 times.
  • The paper gives formulas for bits and passes, and none for rows per box. In a 10-round race on 24 November, with the same code and the same rows per box on both sides, the paper's formula took 1.27 to 1.51 times as long as the tuner's pick and lost all 40 of 40 rounds.
  • All of that gap comes from the paper's passes rule, filled in with its 1999 computer's 64-entry page-address list. The paper's bits in 1 pass tied with the tuner at all 4 sizes.

Words used on this page

Radix join

The join from the paper. It first cuts tables R and S into pieces by the last few bits of each key's hash number, so matching rows land in pieces with the same number. Then it joins piece by piece, each with a small hash table.

Radix bits

How many bits choose the piece. B bits give 2B pieces: 10 bits give 1,024 pieces. 0 bits means no cutting: one big hash table on all of R.

Pass

One trip through a whole table to cut it. With 2 passes, 12 bits are cut as 6 + 6: first into 64 pieces, then each of those into 64 more.

Rows per box

How full each piece's hash table is. 1/8 means 8 boxes for every row; 4 means 1 box for every 4 rows. The code calls a box a "bucket".

ns per row

The time of one whole join in nanoseconds (billionths of a second), divided by the rows in one table. Lower is faster.

Median

The middle value of the runs: half were faster, half slower. One very slow run cannot move it.

Tie

Two settings tie when the fastest run of one was faster than the slowest run of the other.

log2

How many times you double 1 to reach a number. log2(1,024) = 10, because 210 = 1,024. log2(1,536) = 10.585, between 10 and 11.

Page-address list (TLB)

A short list inside the processor of recently used memory-page addresses. A write to a page not on the list waits while the processor looks the address up.

What the tuner changes and keeps fixed

The rules are written down in tuner/SPEC.md as version 1. Changing any fixed item means a version 2, and results of different versions are never compared; the report program refuses to.

What stays the same in every run

Data
N rows in each table. R's keys are 0 to N−1; S's keys are 0, 2, 4, …, so exactly half of S finds a match. Both shuffled with seed 42. A row is 8 bytes: a 4-byte key and a 4-byte row number.
Join code
A copy of experiment 4's radix join, with the same hash function mix. The bits are split evenly over the passes; earlier passes get the extra bit.
Score
Time of one whole join divided by N: cutting R, cutting S, building every piece's table and looking up every row of S. Emptying the boxes is counted. Matches are counted, not written out.
Timing
All memory is set up before the clock starts. One clock read before the join and one after, nothing in between.
Thread
1 thread. On macOS, the highest priority class (macOS cannot keep a thread on one core). On Linux, kept on the core it starts on.
Sizes
Learns at 1,048,576, 4,194,304 and 16,777,216 rows. Checks at 8,388,608 rows. A size that needs more than a quarter of the memory is skipped; 16,777,216 rows needs about 1.4 GB.

The rule it learned, and the check

How the rule is worked out

  1. Rows per piece for each winner: 1,048,576 ÷ 211 = 512 = 29; 4,194,304 ÷ 212 = 1,024 = 210; 16,777,216 ÷ 210 = 16,384 = 214.
  2. Average the powers: (9 + 10 + 14) ÷ 3 = 11.
  3. 211 = 2,048 rows per piece.
  4. Passes and rows per box: the value that won most often. 1 pass and 1/8 won at all 3 sizes.
bits = round(log2(rows ÷ 2,048)), 1 pass, 1/8 row per box

At 8,388,608 rows: 8,388,608 ÷ 2,048 = 4,096, and log2(4,096) = 12, so the rule picks 12 bits.

Is it fair?

Mostly. These are the 5 weak points, largest first.

1 · No-cutting join never tuned
No cutting was timed only at 1/2 row per box, while the radix join got its best box setting. In experiment 6, the no-cutting join at 1/2 took 1.40 times as long as its own best at 4,194,304 rows and 1.29 times at 16,777,216. In the check at 8,388,608 rows, where both joins used 1/8, the radix join was 1.89 times as fast as no cutting, against 2.58 and 2.68 at the learning sizes.
2 · The check is easy to pass
6 of the 7 bits tried at 8,388,608 rows tied with the fastest; the worst, 15 bits, took 5.7% longer. The check also varied only the bits, never passes or rows per box.
3 · The rule averages winners that disagree
The 3 winners mean 512, 1,024 and 16,384 rows per piece, a factor of 32 apart. The rule of 2,048 works because so many settings tie, not because 2,048 is a sharp best.
4 · Stage B assumes the best bits do not depend on rows per box
Stage A picks the top 4 bit settings at 1/2 row per box only. At 1/8 each piece's table is 4 times larger, so the best bits could move. At 16,777,216 rows, 13 bits at 1/8 was never tried. At 8,388,608 rows it was, and it tied (10.79 against 10.75 ns), so this probably cost nothing here.
5 · "Tie" is a loose test
Overlapping fastest-to-slowest ranges. One slow run in the winner's 11 is enough to make almost every setting tie with it.

All the limits

  • One run. The tuner ran once, on one machine. Whether a second run picks the same bits is unknown; with this many ties it could pick anything from 9 to 12.
  • One thread. Experiment 5 showed more threads change the timings.
  • One data set. Unique keys, both tables the same size, half of S matching, 8-byte rows, one shuffle. No repeated or uneven keys in the timed data.
  • Sizes. 1, 4 and 16 million rows, checked at 8 million. Nothing smaller or larger.
  • Ranges. 1/8 row per box is the smallest value tried and won at every size. Bits stop at 18, passes at 3.
  • Fixed choices. Bits always split evenly over the passes; the hash function is always mix.
  • Result rows. Matches are counted, not written out.
  • Cores. macOS cannot keep the thread on one core, so it may move between the 4 fast cores and the 6 slower ones. The slower cores have 64 KB and 6 MB caches instead of 128 KB and 16 MB.
  • No "why". macOS hides the processor's cache-miss counters, so the tuner says which setting is fastest, not why.
  • Linux. The Linux code path has never been compiled or run.
  • Order. The shuffle seed is fixed, so every run uses the same order: repeatable, but not independent.
  • Selection bias. The winner's time comes from the same 11 runs that picked it, which flatters it slightly. The check at 8,388,608 rows is the only fresh measurement.
  • Stale comment. tune.sh says a run takes "about 3 minutes"; the run took 2 minutes 0 seconds.

Formula 1 · page 63

Radix bits: fit one piece in a cache

B = log2(C × 12 ÷ cache size)
  • C is the number of rows in R, the table the hash table is built on.
  • 12 is the bytes one row of R takes, counting its share of the hash table. The paper does not break the 12 down.
  • In plain words: cut R into just enough pieces that one piece plus its hash table fits in the chosen cache. The paper does not say how to round. To make the piece fit, round up.
Worked example · 16,777,216 rows · first cache
  1. All of R plus its table: 16,777,216 × 12 = 201,326,592 bytes.
  2. How many caches' worth: 201,326,592 ÷ 131,072 = 1,536.
  3. log2(1,536) = 10.585. Round up: 11 bits, 211 = 2,048 pieces.
  4. Check: 16,777,216 ÷ 2,048 = 8,192 rows per piece; 8,192 × 12 = 98,304 bytes, which fits in 131,072.
  5. With 10 bits: 16,384 rows = 196,608 bytes, which does not fit.

The paper gives 3 versions, one per kind of memory it could aim at:

Rows (C)C × 12 bytesFirst cache: ÷ 131,072 → log2 → bitsSecond cache: ÷ 16,777,216 → log2 → bitsPage list, 64 entries: ÷ 1,048,576 → log2 → bits
1,048,57612,582,91296 → 6.585 → 70.75 → −0.415 → 012 → 3.585 → 4
4,194,30450,331,648384 → 8.585 → 93 → 1.585 → 248 → 5.585 → 6

  • The first-cache version always gives pieces of 8,192 rows (96 KiB). The paper calls it "phash L1" and says it "really needs the multi-pass radix-cluster algorithm".
  • The second-cache version always gives pieces of 1,048,576 rows (12 MiB). At 1,048,576 rows the whole table already fits, so it says: do not cut.
  • The page-list version aims at the memory the list covers: entries × page size. With the paper's 64 entries that is 64 × 16,384 = 1,048,576 bytes. The M5's number of entries is unknown, so its true answer is unknown.
Formula 2 · page 60

Passes: at most 64 pieces per pass

The paper: "Up to 6 bits, using just one pass yields the best performance. … With more than 6 bits, two passes perform better than one. … three passes should be used with more than 12 bits, and four passes with more than 18 bits. Thus, the number of clusters per pass is limited to at most the number of TLB entries (64)." It also says performance "strongly depend[s] on even distribution of bits".

P = bits ÷ log2(entries), rounded up · with 64 entries: P = bits ÷ 6, rounded up

  • This uses the paper's 64, because macOS does not report the M5's number. If the M5's list holds at least 2,048 entries (211), the same rule gives 1 pass at every size above.
  • The paper names a second limit: one pass slows down once it writes to more pieces than the second cache has blocks. Experiment 3 fits it on the M5. At 17 bits, 1 pass and 2 passes took about the same time (2.56 and 2.60 ns per row), and 217 = 131,072 is exactly the number of blocks in the M5's second cache. From 18 bits, 2 passes won. Without the cache-miss counters this match cannot be proven to be the cause.
Formula 3

Rows per box: no formula

The paper never says how many boxes the hash table should have. Its time formulas assume "a bucket-chain length of 4" (page 62), which is about 4 rows per box, the same as Varun's rule in commit d28429e. Varun's commit gives no reason, so whether it came from the paper is unknown.

On the M5, 4 rows per box took 1.70 to 1.91 times as long as 1/8 at the same bits (tuner stage B).

Two more numbers from the paper
Its measured best
"partitioned hash-join performs best with cluster size of approximately 200 tuples" (page 63). An observation, not a rule. Copied to the M5 as bits = log2(C ÷ 200), rounded: 1,048,576 ÷ 200 = 5,242.9 → 12.36 → 12; 4,194,304 → 20,971.5 → 14.36 → 14; 8,388,608 → 41,943.0 → 15.36 → 15; 16,777,216 → 83,886.1 → 16.36 → 16. On the paper's own 32 KB cache, its first-cache rule gives about 2,730 rows per piece, so its measured best was smaller than its own rule.
The other join
The paper's nested-loop join, which compares every row of a piece with every row of the matching piece, uses B = log2(C ÷ 8): 17, 19, 20 and 21 bits at the 4 sizes. We did not build that join.
The time formulas · pages 60 and 62

Cannot be worked out for the M5

The paper also predicts the time of the hash join. The formula for cutting has the same shape, times the number of passes. Each "misses" term is itself a formula built from the sizes above.

The paper says the best bits came from "putting together the experimental data we obtained on both cluster- and join-performance": it also chose by measuring.

The race: formula against tuner

Run on 24 November in 26 seconds, saved in m5-pro/tuner/paper-race/. The race program includes the tuner's own source file, so the join, the data, the clock, the answer check and the memory setup are the same lines of code on both sides. Only the settings differ. Did we beat the paper?

On this Mac, the tuner's settings beat the paper's formula: 40 of 40 rounds, by 1.27 to 1.51 times. All of that gap comes from one number the formula needs and macOS does not report: the size of the page-address list. With the paper's 1999 value of 64, the formula says 2 passes. If the M5's list allows 1 pass, the paper's settings tie with the tuner's.

Where the paper held up

  • Bits The first-cache rule picks good bits: in 1 pass they tied with the tuner at all 4 sizes, 1.02 to 1.09 times its time.
  • Main claim Cutting first makes the join faster: the tuner's pick was 1.83 to 1.99 times as fast as no cutting with the same rows per box.
  • Passes The 6-bits-per-pass limit comes from the 1999 computer. On the M5, 1 pass stays as fast as 2 up to 17 bits.
  • Rows per box No rule. Its assumed 4 rows per box took 1.70 to 1.91 times as long as 1/8.

What can be said to the professor

  • With the same join code and the same rows per box, the paper's formula took 1.27 to 1.51 times as long as the tuner's settings on the M5, and lost 40 of 40 rounds.
  • All of that comes from the 6-bits-per-pass rule, built on the 1999 computer's 64-entry page-address list. The paper's bits rule still works: in 1 pass its bits tie with the tuner's.
  • The paper gives no rule for rows per box. Timing found 1/8 (tuner) and 1/4 (experiment 6).
  • A 2-minute timing tool finds these settings without knowing any hardware sizes. It automates what the paper did by hand.
  • Say "the tuner's settings beat the paper's formula filled in with its 1999 numbers". The algorithm is the paper's, unchanged; only the way of choosing its 3 settings differs.

What would make it airtight

  1. Measure the M5's page-address list. Read one byte from each of a growing number of 16 KiB pages; the time per read jumps once the pages outnumber the entries. Then rerun the race with that number in formula 2 (PAPER_TLB_ENTRIES in paper-race/plan.py).
  2. Repeat the race and the tuner. Run ./run.sh 3 times, and the tuner itself 3 times, to show whether the results and the tuner's picks repeat.
  3. Tuner version 2: tune the no-cutting join's rows per box too, add 1/16 row per box, and retest passes and rows per box in the check.
