Words used on this page

Each technical word below is used later with exactly this meaning.

Join

Matching the rows of two tables that share a key, for example orders with customers. Our two tables are called R and S. A row is 8 bytes: a 4-byte key and a 4-byte row number.

Hash table and boxes

A row of numbered boxes. Each row of R is filed in one box, chosen from its key. To find the matches for a row of S, the join opens one box instead of searching all of R. The code and reports call a box a "bucket".

Chain

The list of rows that landed in the same box. A lookup checks every row in the chain.

Rows per box

Rows divided by boxes. ½ row per box means 2 boxes for every row. 4 rows per box means 1 box for every 4 rows.

Hash function

A fixed formula that turns a key into a box number. Ours is called mix. A good one spreads keys evenly over the boxes.

Cache

Small, fast memory inside the processor that keeps copies of recently used data. The M5 has 128 KB per fast core and 16 MB shared by its 4 fast cores. A read from the cache took 2.6 ns; a read from main memory took 34.3 ns (experiment 1).

Simple join

The Week 2 hash join: one big hash table on all of R, then a lookup for every row of S.

Radix join

The paper's join. It first cuts R and S into pieces using the last few bits of each key's hash number, so matching rows land in pieces with the same number. Then it joins piece 1 with piece 1, piece 2 with piece 2, and so on, each with a small hash table that fits in the cache.

Radix bits (B)

How many bits choose the piece. B bits give 2B pieces: 8 bits give 256 pieces, 12 bits give 4,096.

Pass

One read through a whole table to cut it. With 2 passes, 12 bits are cut as 6 + 6: first into 64 pieces, then each of those into 64 more.

Thread and speedup

A thread is one worker. The M5 has 4 fast (performance) cores and 6 slower (efficiency) cores. Speedup is the time with 1 thread divided by the time with N threads; perfect sharing over 4 threads gives 4.

Median and tie

The median is the middle value of the runs: half were faster, half slower. Every time on this page is a median. Two settings tie when the ranges from their fastest to their slowest run overlap.

ns and ms

A nanosecond (ns) is a billionth of a second; a millisecond (ms) is a thousandth. "ns per row" is the whole time divided by the rows in one table.

Fixes to the report scripts

  • The partitioning report called a one-time spike at 1 bit "cost rises from 1 bit". Now a rise counts only if every larger number of bits also stays more than 30% above the flat level, the middle value of 2 to 8 bits.
  • The join report's cost model read only experiment 3 rows labelled with 4 KB pages. On the Mac the label is "default", so it silently used none of them. It now reads both labels.
  • The clock-read share of each run is computed from the data. Before, the report printed "under 1%" as fixed text.
  • The "Interference" line no longer describes cloud-server effects, which a laptop does not have. The final report quotes thread speedup at 4 threads, one per fast core.

Two measuring mistakes we fixed

Both were in the programs for experiments 4 and 5, from the separate folder. The separate folder itself is unchanged. The old behaviour of each can still be switched on, so the difference can be shown live. m5-pro/DESIGN-FLAWS.md has the full explanation.

Mistake 1 · experiment 4

The radix join read the clock inside its own timing

What it did
To report build time and lookup time separately, the program read the clock twice per piece, inside the timed join. With 14 bits there are 16,384 pieces, so 32,768 clock reads. At about 9 ns each that is about 0.3 ms, in a join that takes about 1.4 ms at 100,000 rows.
Effect
Settings with many pieces looked slower than they were. That pushes the choice of bits down, and choosing the bits is the point of experiment 4.
How we found it
The old report said the clock reads cost "under 1%". That was fixed text, not a measurement. With 9 ns per read, the share at 14 bits and 100,000 rows comes to 18% on paper.
Fix
The join is timed once, with no clock reads inside. Build time comes from a separate build-only pass after each run. The old way: --timing per-partition.

Mistake 2 · experiment 5

The threaded simple join waited after every insert

What it did
When several threads add rows to one shared hash table, each insert must be all-or-nothing, or a row is lost when two threads hit the same box at once. The program also told every insert to wait until all earlier memory writes of its core had finished. Each insert writes to a random place in a 128 MB array, a slow trip to main memory, so each insert waited for the previous slow trip. A core can normally keep dozens of such trips going at once.
Why the wait was not needed
No thread reads the table until every thread has finished the build, and that finishing point already makes every write visible to all threads.
How we found it
With 1 thread, building the table took 568 ms in experiment 5, while the plain build in experiment 4 took 75 ms for the same 16,000,000 rows. We then timed 4 ways of inserting with 1 thread (table below).
Fix
Each insert is one all-or-nothing swap with no waiting. A checking tool (ThreadSanitizer) ran all 5,524 test cases and found no two threads touching the same memory unsafely. The old way: --insert cas-release.

Two more facts about measuring
Whole runs shift
A repeat of experiment 5, 15 minutes after the official run, was 5% to 18% faster for both joins at every thread count. The ratio moved much less: the radix join over the simple join with 4 threads was 2.3 in the official run and 2.35 in the repeat. So we compare times within one run, and ratios across runs. Folder: results/05-parallel-join-repeat.
Kept on purpose
The Week 2 program (experiment 2) requests the hash table's memory inside the build timer, so the operating system's setup of each 16 KB page is counted as build time. More boxes means more pages. We kept it because report 2 reproduces the Week 2 report. Experiments 3 to 6 set up all memory before any timer starts.

What experiments 1 to 5 measured

All on the M5, after both fixes. Every run checks its answer against the known number of matches. Each round runs every setting once in a new random order, so a slow moment of the laptop lands on different settings each round.

Experiment 1 · stride scan

Does the gap between memory reads change the time?

Setup
200,000 single-byte reads per scan. The gap between reads goes from 1 to 1,024 bytes (11 values). 3 warm-up rounds, then 30 recorded runs of each.
Result

After emptying the cache, a gap of 256 bytes took 20 times as long as a gap of 1 byte for the same number of reads: 4.96 against 0.24 ns per read. At a gap of 1, one 128-byte memory block serves 128 reads; from a gap of 128, every read needs its own block from main memory.

Experiment 2 · simple hash join

How does a plain hash join slow down as tables grow?

Setup
10,000 to 2,000,000 rows per table (5 sizes). R's keys are 0 to N−1; S's keys are 0, 2, 4, …, so half of S finds a match. 1 warm-up, then 7 recorded runs. Run with both box rules: Week 2 (2 boxes per row) and Varun's (1 box per 4 rows).
Result

Time per row grew from 4 ns at 10,000 rows to 27 ns at 2,000,000 rows, for the same work per row. Varun's rule took 1.65 to 2.52 times as long as the Week 2 rule at every size: 136.4 against 54.0 ms at 2,000,000 rows.

Experiment 3 · radix partitioning

How many pieces can one pass cut a table into before it slows down?

Setup
16,777,216 rows of 8 bytes (128 MB). 0 to 20 bits (1 to 1,048,576 pieces), in 1, 2 or 3 passes. 1 warm-up, then 15 recorded runs of each.
Result

One pass cost about 1.7 ns per row (the middle value of 2 to 8 bits). From 16 bits (65,536 pieces), every value stayed more than 30% above that, reaching 5.6 ns at 20 bits. Two passes beat one pass only from 18 bits (262,144 pieces). The paper's limit, set by 1999 hardware, was about 6 bits (64 pieces) per pass.

Experiment 6: the professor's question

Number of boxes: result
  • The fewest boxes that tied with the fastest setting at every size was ¼ row per box (4 boxes per row), for both joins.
  • Why a best value exists: at 16,777,216 rows the simple join spent 306 ms building with 1/16 row per box against 16 ms with 8, because every box is emptied before the rows go in. Lookups went the other way: 265 ms against 7,887 ms, because a lookup walks a chain and each row in it is one more wait for memory.
  • Memory for the boxes, simple join at 16,777,216 rows: 256 MB at ¼ row per box, 128 MB with the Week 2 rule, 16 MB with Varun's rule. Varun's rule uses the least memory and took 4.87 times as long.
  • The radix join cared less: Varun's rule took 1.71 times as long, because each piece's small table sits in the cache, where walking a longer chain is cheap.
  • For the radix join at 16,777,216 rows, 1/8 and ¼ row per box were 0.5% apart (195.2 and 194.2 ms). 1/16 took 211.9 ms, 9.1% longer than ¼.
Hash function: result
  • Over every size and setting, mix left a share of empty boxes within 0.06 percentage points of what a perfectly random hash function leaves. So mix spreads our keys evenly, and the chain lengths are what chance gives.
  • On keys 0, 1, 2, …, the cheapest function (use the key itself as the box number) made the simple join 2.68 times as fast as mix: 8.7 against 23.4 ms.
  • On keys that are multiples of 64, the same cheap function used only 1 box in 64, and the simple join took 205.8 ms against 23.5 ms with mix: 8.77 times as long.
  • In the simple join, mix was never the fastest of the 5 functions on any of the 3 kinds of keys, and never more than 2.7 times as slow as the fastest.

Which of the paper's conclusions hold

The paper is Boncz, Manegold and Kersten, VLDB 1999. Its claim: on modern computers a join is slowed by waiting for memory, not by arithmetic, so it should be organized around the cache. This table is from report 07.

Why some conclusions are weaker on the M5

  • Passes. In 1999 the processor's list of recently used memory-page addresses held 64 entries or fewer, so one pass could write to about 64 pieces. On the M5, one pass stayed within 30% of its flat level up to 15 bits (32,768 pieces).
  • Cache size. The M5's second cache is 16 MB, so pieces can be much larger than the paper's.
  • Waiting for memory in parallel. A modern core keeps many memory reads going at once. That shrinks the simple join's penalty, which limits the radix join's lead to 2.49 times in our runs.

The tuner

A separate program in m5-pro/tuner/ that uses no file outside that folder. It finds the radix join's best settings on whatever computer runs it, by timing the join. It never reads the cache sizes; the timings already contain their effect.

What it changes
3 settings. Radix bits: 0 to 18. Passes: 1, 2 or 3. Rows per box: 1/8, 1/4, 1/2, 1, 2, 4.
What it measures
Nanoseconds per row for one whole join, cutting included. Lower is better. Every run's answer is checked; a wrong answer stops the tuner.
What is frozen
The join code, the data, mix, 1 thread, the timing rules, the search steps and the sizes are written down in tuner/SPEC.md as version 1. Changing any of them means a version 2, and results of different versions are never compared; the report program refuses to.
How it searches
Stage A times every bits-and-passes pair at ½ row per box, 3 rounds. Stage B takes the best 4 pairs with all 6 rows-per-box values, 3 rounds. Stage C races the best 5 plus up to 2 reference settings (no cutting, and stage A's winner), 11 rounds. It does this at 1,048,576, 4,194,304 and 16,777,216 rows.
The rule it learns
From the 3 winners, it learns how many rows one piece should hold. Then it checks that rule at 8,388,608 rows, a size it did not learn from.
Commands
./tune.sh for a real run; ./tune.sh --quick checks that everything works in about 2 seconds.

Result on the M5 (run of 23 November, 2 minutes 0 seconds)
  • The bottom of the curve is flat. At 16,777,216 rows, every value from 9 to 12 bits came within 5% of the lowest point (8 to 13 bits at 1,048,576 rows; 9 to 13 at 4,194,304).
  • Rows per box mattered more than bits. 1/8 row per box made the join 1.19, 1.19 and 1.14 times as fast as ½ row per box at the 3 sizes.
  • The learned rule: about 2,048 rows of R per piece (about 16 KB of rows plus a 72 KB table), 1 pass, 1/8 row per box.
  • The check at 8,388,608 rows: the rule chose 12 bits, the fastest was 11 bits, and the rule's choice took 1.002 times as long: a tie.
  • Time: 4 s at 1,048,576 rows, 21 s at 4,194,304, 1 min 30 s at 16,777,216, 5 s for the check. The PDF report takes under 1 second.

Two limits of the tuner

  • 1/8 row per box is the smallest value version 1 tries, and it won at every size. Testing smaller values needs version 2. Experiment 6, with a different setup (12 bits), measured 1/16 at 16,777,216 rows: 9.1% slower than ¼ for the radix join.
  • It has run only on this Mac. Its Linux code, which keeps the thread on one core, has never been compiled or run.

The paper's formula against the tuner

The paper chooses settings from the computer's numbers instead of timing them. We wrote its rules down, computed what they choose on the M5, and timed those choices against the tuner's in one run: each setting 11 times in a shuffled order, 39 seconds in total.

Bits rule
Cut until one piece of R plus its hash table fits in the fastest cache, 128 KB on the M5.
Passes rule
At most 6 bits (64 pieces) per pass. 64 is the limit of the paper's 1999 computer. macOS does not report the M5's number, so we used the paper's.
Rows per box
The paper gives no rule. Our experiments used ½, so the formula got ½.

  • The bits rule works: the formula's bits came within 8% of the tuner's. Values under 1 mean the formula's bits were slightly faster in this run.

What we could not measure

  • Cache misses. macOS does not let a program read the processor's counters of cache misses. Every cache explanation here comes from timings and data sizes.
  • Keeping a thread on one core. macOS decides which core runs each thread.
  • Large memory pages. macOS does not let a program choose its page size, so the page-size half of experiment 3 was skipped.
  • Repeated or uneven keys. Every key appears once in the timed data. Repeated keys would make some pieces and chains much longer.
  • Writing the result. The joins count matches instead of writing every matched pair, which would add the same cost to both joins.
  • One table design. Every join uses chained boxes with a power-of-two count. Other designs would have other best settings.
  • The paper's nested-loop variant. The paper also joins very small pieces without a hash table. We built only the hash-table version.
