Radix hash join project · Apple M5 MacBook Pro · 22 November

How We Test Joins

What each of our six experiments asks, how it is set up, what it measured on the M5, and how we turn timings into a conclusion.

Short version. Each experiment asks one question.

We change one setting at a time and keep everything else the same. We repeat every setting many times, check every answer, and compare the middle value of the runs.

All six experiments ran on one laptop, an Apple M5 MacBook Pro, so their times can be compared with each other.

The question behind all six

A join matches rows of one table with rows of another that share a key, for example orders with customers. Our joins use a hash table: a row of numbered boxes where each row is filed by its key, so a match can be found by opening one box instead of searching everything.

In 1999 Boncz, Manegold and Kersten argued that on modern computers the slow part of a join is not the arithmetic but waiting for memory. A processor keeps small, fast copies of recently used memory, called caches. On the M5, a random read took 2.6 nanoseconds when the data was in a cache and 34.3 nanoseconds when it had to come from main memory (measured at the start of experiment 1). Their fix, the radix hash join, first cuts both tables into small pieces that fit in the cache, then joins piece by piece.

Experiments 1 to 5 test that argument step by step, on today's hardware. Experiment 6 tests a choice inside every hash table that we had never tested: how many boxes it has, and how evenly the hash spreads keys over them.

Rules every experiment follows

These rules are what make one timing comparable with another.

Check every answer

Every timed run checks its result: the number of matches and a checksum of the matched row numbers must equal the expected values. Each join and partitioning program also has a test mode that checks 107 to 5,751 small cases against a slow but obviously correct method.

Throw away the first run

The first run of a setting fills caches and wakes up the processor. It is checked but not recorded.

Shuffle the order every round

Each round runs every setting once, in a new random order. If the laptop is slow for a moment, that slowness lands on different settings each round instead of always on the same one.

Report the middle value

We report the median: half of the runs were faster, half slower. One run slowed by a background program moves the average a lot but the median hardly at all.

Prepare memory before the clock starts

From experiment 3 on, all memory is requested and written once before timing. Otherwise the first touch of each memory page, which the operating system handles, would be counted as join time.

Same data every time

Inputs come from a fixed random seed (42), so every run of every experiment sees exactly the same rows in the same order. Experiment 4 repeats with two other seeds to check that one particular order is not special.

Experiment 1 · stride scan

Does the gap between reads change the time?

Why
The cheapest way to see memory cost on its own. Every scan does the same work, reading 200,000 single bytes and adding them up. Only where the bytes sit changes.
What changes
The stride, meaning the gap between two reads: 1, 2, 4, … 1,024 bytes (11 values). And whether the cache was emptied first, or the same bytes were just read.
What stays fixed
200,000 reads per scan, one 256 MiB array, one thread.
Repeats
3 warm-up rounds, then 30 recorded runs of every stride and method, in a new order each round.
Mac change
The Ryzen version emptied the cache with a special instruction. Its Apple counterpart did nothing measurable: random reads took 2.6 ns before it and 2.6 ns after. So the Mac version reads a separate 512 MiB array first, after which reads took 34.3 ns.
How we conclude
Compare the median time per read across strides. A flat line would mean memory layout does not matter.
Result on the M5

After emptying the cache, stride 256 took 20 times as long as stride 1 for the same number of reads (4.96 against 0.24 ns per read). At stride 1, one 128-byte cache line serves 128 reads; from stride 128 on, every read needs its own line from memory.

Experiment 2 · simple hash join

How does a plain hash join slow down as tables grow?

Why
This is the baseline every later experiment compares against.
How it works
Build: file every row of the left table into the hash table. Probe: for every row of the right table, open its box and compare keys with every row in that box.
What changes
Rows per table: 10,000, 100,000, 500,000, 1,000,000, 2,000,000. And, new tonight, the number of boxes: the Week 2 rule (2 boxes per row) against Varun's rule (1 box per 4 rows).
What stays fixed
Left keys 0 to N−1, right keys 0, 2, 4, … so half of the probes find a match. Both tables shuffled. Hash function mix.
Repeats
1 warm-up, then 7 recorded runs per size.
How we conclude
Divide time by rows. If a join only did more work as tables grew, time per row would stay flat. If it rises, each row got more expensive, which points to memory.
Result on the M5

Time per row grew from 4 ns at 10,000 rows to 27 ns at 2,000,000 rows, for the same work per row. Varun's rule was 1.65 to 2.52 times slower at every size (136.4 against 54.0 ms at 2,000,000 rows). Why, and what is still untested, is on the Hash Bucket Lab page.

Experiment 3 · radix partitioning

How many pieces can one pass cut a table into before it slows down?

CountRead every row, take the lowest B bits of its hash, and count how many rows go to each of the 2B pieces.
PlanAdd the counts up, so each piece knows where it starts in the output.
CopyRead every row again and copy it to the next free slot of its piece.
Why
The copy step writes to 2B places at once. The paper says too many places overwhelm the cache and the address-translation cache (the TLB), so it splits the bits over several passes, for example 12 bits as 6 + 6.
What changes
Bits B from 0 to 20 (1 to about 1 million pieces), in 1, 2 or 3 passes.
What stays fixed
16,777,216 rows of 8 bytes (128 MiB), the same hash as experiment 2, one thread.
Repeats
1 checked warm-up, then 15 recorded runs of every setting, in a new order each round. Typical spread between runs: 4% of the average.
How we conclude
Cost per row against B. The "flat level" is the median of 2 to 8 bits. A slow-down counts only if it lasts: every larger B must also stay more than 30% above the flat level.
Result on the M5

One pass costs about 1.7 ns per row from 2 to 15 bits, close to a plain copy (1.85 ns at 0 bits). From 16 bits (65,536 pieces) it stays slower, reaching 5.6 ns at 20 bits. Two passes only win from 18 bits (262,144 pieces). On 1999 hardware, whose address-translation cache held 64 entries, the paper's limit was about 6 bits (64 pieces).

Experiment 4 · simple against radix hash join

Does cutting the tables into pieces first make the join faster?

Cut the left tableOne or two partitioning passes, as in experiment 3.
Cut the right tableSame bits, so matching keys always land in pieces with the same number.
Join piece by pieceFor piece p: build a small hash table from the left piece, then probe it with the right piece. Each small table fits in the cache.
Why
Cutting costs an extra read and write of both tables. The question is whether faster lookups in small tables pay for that.
What changes
Rows per table: 100,000, 1 million, 2 million, 4 million, 8 million, 16 million, 32 million. Radix bits 2 to 18 (skipped when pieces would hold fewer than 4 rows), in 1 or 2 passes. Plus the simple join at every size.
What stays fixed
Both joins share the same hash table code and the same inputs as experiment 2. Inside a piece, boxes are chosen from the hash bits above the B bits used for cutting (all rows in a piece share their lowest B bits).
Repeats
1 checked warm-up, then 15 recorded runs of every setting, in a new order each round. Then the same at 3 sizes with 2 other data seeds, 7 runs each.
Timing
The piece-by-piece join is timed as one block with no clock reads inside it. The split into build and probe time comes from a separate build-only pass after each run. (v2 read the clock twice per piece inside the timing; fixed tonight, see below.)
How we conclude
For each size, find the fastest radix setting. "Clearly faster" means its slowest run beat the simple join's fastest run. Settings whose runs overlap with the best one count as ties. Speed-up ranges come from resampling the recorded runs 4,000 times (a bootstrap): the middle 95% of the resampled ratios.

Result on the M5

At 32,000,000 rows the radix join took 456 ms and the simple join 1118 ms: 2.45 times as fast, using 12 bits in one pass. From 8,000,000 rows up, every recorded radix run beat every recorded simple run. At 100,000 rows, where everything fits in the cache anyway, the ratio was 0.98. The simple join's cost per row grew from 11 ns at 100,000 rows to 35 ns at 32,000,000 rows (highest: 35 ns at 32,000,000 rows); the radix join stayed between 11 and 14 ns. A simple cost model picked a setting within run-to-run noise of the fastest at 7 of 7 sizes; its worst pick was 3% slower. The model was fitted to these same runs, so this shows it describes the data well, not that it can predict a new machine.

Experiment 5 · threads

Do the joins get faster with more processor cores?

Why
The assignment's extension: run each phase with 1, 2 and 4 threads (independent workers) and report time per phase and speed-up.
How work is shared
Simple join: every thread files its share of the left rows into one shared table, using one all-or-nothing swap on the box so no row is lost; then every thread probes with its share of the right rows. Radix join: every thread counts its share of rows, the counts are combined so each thread knows exactly where to write, then all copy at once with no locks. Pieces are then handed out 16 at a time to whichever thread is free.
What changes
Threads: 1, 2, 4, 8. The M5 has 4 fast (performance) cores and 6 slower (efficiency) cores; 8 shows what happens once threads spill onto the slower ones.
What stays fixed
16,000,000 rows per table. Radix setting 12 bits in 1 pass, picked automatically: the fastest setting at this size in experiment 4.
Repeats
1 checked warm-up, then 15 recorded runs of every thread count and join, in a new order each round.
How we conclude
Every phase ends with all threads waiting for each other, so a phase's time is the time of its slowest thread. Speed-up = time with 1 thread ÷ time with N threads. Perfect sharing would give N.

With 4 threads, one per fast core, the radix join ran 3.39 times as fast as with one thread and the simple join 3.00 times. The radix join gained more from threads and finished first at every thread count (73 against 167 ms with 4 threads). With 4 threads the radix join's cutting phase sped up 2.91 times and its probe phase 3.69 times. With 8 threads: radix 5.22×, simple 3.89×.

Fixed tonight: in v2 every insert of the simple join waited until all earlier memory writes had finished, even with one thread. Its 1-thread build took 568 ms, which made its speed-up look 3.78× at 4 threads. Each insert is now one swap with no waiting; the 1-thread build takes 78 ms. The plain build of experiment 4, with no atomic operations at all, took 58 to 251 ms over its runs (middle value 105 ms), so the safe insert now costs nothing extra.

Experiment 6 · boxes and hash functions

How many boxes should the hash table have, and does the hash spread keys evenly?

Why
The professor's question. Week 2 used 2 boxes per row (0.5 rows per box) and Varun's commit changed it to 1 box per 4 rows (4 rows per box). Neither was tested, and nobody checked how evenly the hash spreads our keys.
What changes
Rows per box: 1/16, 1/8, 1/4, 1/2, 1, 2, 4, 8. Rows per table: 65,536, 524,288, 4,194,304, 16,777,216. Both joins; the radix join uses the same rule inside every piece. A second run at 1,048,576 rows tries 5 hash functions on 3 key patterns.
What stays fixed
The table design (a chain per box), box counts that are powers of two, the timing rules of experiment 4 after its fix, and one thread.
Repeats
1 checked warm-up, then 7 recorded runs of every setting, in a new order each round.
How we conclude
For each size and join, the fastest rows-per-box value wins; values whose runs overlap with it are ties. The rule to keep is the fewest boxes that tie with the fastest at every size, because fewer boxes use less memory. How evenly keys spread is measured on the real tables and compared with what a perfectly random hash would give.

Result on the M5

At 16,777,216 rows the simple join was fastest with 1/4 rows per box; the Week 2 rule took 1.29× as long and Varun's rule 4.87×. The radix join was fastest with 1/4 rows per box and cared less: Varun's rule took 1.71× as long, because its small tables sit in the cache, where walking a longer chain is cheap. For both joins the fewest boxes that tied with the fastest at every size was 1/4 rows per box.

Our hash, mix, left a share of empty boxes within 0.06 percentage points of what a perfectly random hash gives, at every size and setting. So mix spreads our keys evenly; the long chains at 4 rows per box are just what chance gives.

Fixed tonight

  • Clock reads inside the radix join's timing. v2 read the clock twice per piece inside the timed join, about 8 ns per read. With many small pieces that was a real share of the run: at 14 bits and 100,000 rows the old way measured 1.525 ms and the clean way 1.382 ms. Now the join is timed as one block.
  • Slow one-thread build in experiment 5. See experiment 5 above: 568 ms before, 78 ms after.
  • Box count never tested. Experiment 6 now tests it.

Both old ways can still be run for comparison (--timing per-partition, --insert cas-release). DESIGN-FLAWS.md in the m5-pro folder explains both.

Weak spots we know about

  • No cache-miss counts. macOS does not let a program read the processor's built-in miss counters, so every cache explanation here is inferred from timings and data sizes.
  • No core pinning. macOS decides which core runs each thread. We ask for the highest priority class, which macOS keeps on the fast cores.
  • Unique keys only. Every key appears once. Experiment 6 adds two other key patterns, but repeated keys or uneven data would make some pieces and chains much longer.
  • One table design. Every join uses chained boxes with power-of-two counts. Other designs (open addressing, boxes that hold several keys) would have other best settings.
  • Matches are counted, not written out. A real join writes every matched pair, which adds the same cost to both joins.
