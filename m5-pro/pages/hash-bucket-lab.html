Hash Bucket Lab

How our hash join files rows into buckets, how evenly our hash function spreads them, and why the number of buckets is a choice we have to test instead of guess.

Short version. A hash table is a row of numbered boxes, called buckets.

A hash function turns each key into a box number. Rows that get the same number share a box, in a short list called a chain.

To find a key, the join opens one box and checks every row in it. More boxes means shorter chains, but the row of boxes takes more memory.

What our code does today

The simple hash join (src/hash_join.c) keeps two arrays. The bucket array holds, for each box, the position of the first row in its chain. The next array holds, for each row, the position of the next row in the same chain.

To pick a box, it scrambles the key with a fixed formula and keeps the lowest bits of the result. The formula is mix, the finishing step of a published random-number generator called SplitMix64. It uses shifts, exclusive-or and two multiplications. The number of boxes is always a power of two, so "keep the lowest bits" is the same as "take the remainder".

How many boxes? Two rules exist in our history, and neither was chosen by an experiment:

  • Week 2 rule (commit 4fd6a67): at least 2 boxes per left row, rounded up to a power of two. The notes give one reason: fewer rows per box means shorter chains, at the cost of memory.
  • Varun's rule (commit d28429e, 22 November): about 1 box per 4 left rows, rounded up to a power of two. The commit gives no reason.

We also never checked how evenly mix spreads our keys. The lab below and the numbers after it do that check.

The hash is fine. With both rules the share of empty boxes matches a perfectly random hash to one decimal place, and so does every other chain length (try it in the lab). So mix spreads our keys as evenly as we could ask.

The bucket count is a real trade-off. Each lookup reads one box, then two arrays for every row in the chain: the row's key and its link to the next row. Those reads land at random places.

  • The Week 2 rule checks about 1 row per lookup on average over our probes (half find a match, half don't), because our code walks the whole chain even after a match, but its 32 MiB box array is twice the size of the M5's 16 MiB fast memory (its L2 cache), so most box reads go to main memory.
  • Varun's rule shrinks the box array to 4 MiB, which fits in that fast memory, but each lookup checks about 4.3 rows, so it makes about 4 times as many random reads into the row arrays.

Which effect wins depends on the machine, so we timed both rules on the M5 tonight (experiment 2, 7 runs per size after 1 warm-up run, medians).

Radix join

One hash value, two jobs

The radix join uses the scrambled key twice. Its lowest B bits choose the partition. Inside a partition, every row has the same lowest B bits, so those bits can't tell rows apart any more. The bucket number must come from the bits above them. Our radix join does this: hash_build and hash_probe in include/common.h shift the hash right by B before keeping the bucket bits.

Correct: bucket bits start above the partition bits
Mistake: bucket bits taken from the bottom again

Measured at our real size: with 8 partition bits, partition 0 holds 7,814 rows and gets 16,384 boxes. Taking the bucket bits from above the partition bits, the rows use 6,222 boxes and the longest chain is 6 rows. Taking them from the bottom again, the rows can only reach 64 boxes, and the longest chain is 147 rows.

What we never measured

Our professor's point stands. Before tonight every timing used one bucket rule and one hash function. Tonight's run compared two bucket rules, but two points can't show where the best one is. The hash check above settles one half for our keys: mix spreads them like a random hash. The other half, the bucket count, needs the sweep below.
